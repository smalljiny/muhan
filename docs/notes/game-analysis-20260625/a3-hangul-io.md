# A3 한글 입출력·방향 매핑

> 무한의 한글 입출력·방향 매핑·인코딩 처리 경계를 oracle에서 규명한다. 서버 i18n 경계 결정과 명령 토크나이저 설계의 입력. 이슈 #3. 출처는 `legacy/muhan/src`(EUC-KR, byte-level). 코드 이식이 아니라 동작 추출.

## 개요

무한의 한글 처리를 관통하는 **단 하나의 불변식**은 **"EUC-KR은 ASCII-투명(byte-transparent)"** 이다. 서버는 한글을 **디코딩하지 않는다**. 입력은 raw byte로 링버퍼에 쌓이고, 명령·출구·대상 매칭은 모두 **byte-exact `strcmp`**이며, 출력도 raw byte로 그대로 흘려보낸다. "인코딩 처리 경계"는 사실상 **존재하지 않는다** — 게임 전체가 단일 바이트열 공간에서 동작한다.

이 byte-투명성이 성립하는 이유는 EUC-KR 완성형 한글이 **항상 고비트 바이트 쌍**으로만 표현되기 때문이다(`is_hangul`: 선행 0xB0–0xC8, 후행 0xA1–0xFE). ASCII 구분자(공백 0x20, `#` 0x23, 문장부호 `.`/`!`/`?`)는 모두 < 0x80이라 **2바이트 한글 내부에 절대 끼어들 수 없다**. 따라서 바이트 단위로 짠 토크나이저·비교 코드가 한글에서 그대로 옳게 동작한다.

핵심 발견 6가지:

| # | 발견 | 성격 |
|---|------|------|
| 1 | **인코딩 경계 없음** — 입출력 양방향 raw EUC-KR byte, 디코딩 0회 | 형상(재설계) |
| 2 | **방향 매핑은 `move()`에 인라인** — `get_exit_char()`(han.c)는 호출자 0의 dead code, 동일 로직이 `command2.c`에 복제됨 | 콘텐츠(매핑표) + 형상(중복 제거) |
| 3 | **조합형 변환(KStbl)은 I/O가 아니라 언어 분석용** — 받침 추출(조사 선택)·초성 추출(파일 버킷팅) 두 용도뿐, 완성형↔조합형 I/O 변환은 없음 | 분기(아래 §3) |
| 4 | **출력측 조사(josa) 자동선택** — `%j` 포맷 + `Josa[6][2]` 테이블 + 받침 검사 | 콘텐츠(규칙) |
| 5 | **대각선 방향은 데이터에 존재하나 numpad/jamo 별칭은 비활성**(주석 처리) — 전체 단어 입력으로만 도달 | 콘텐츠(결정 필요) |
| 6 | **백스페이스는 바이트 단위** — 2바이트 한글의 반쪽만 삭제하는 read-safe / edit-unsafe 비대칭 | 형상(클라이언트로 이관) |

## 1. 입력 바이트 경로 — 불변식의 실제 동작

입력 한 줄의 수명: 소켓 → 링버퍼 → 라인 추출 → 토큰화 → 디스패치.

```
read(fd, buf, 127)                 io.c:451   ← raw byte, 디코딩 없음
   │  · byte filter (아래)
   ▼
Ply[fd].io->input[] (ring buffer)  io.c:481   ← byte 단위 적재, CR/LF에 commands++
   ▼
server_loop가 라인 1줄 추출         io.c:792   (13/10 = 라인 종결)
   ▼
command(fd, param, str)            command1.c:415
   │  · lowercize(str, 0)          ← ASCII 'A'–'Z'만 소문자화, 한글 byte 무영향
   ▼
parse(str, &cmnd)                  command1.c:505   ← 공백/`#`/문장부호로 토큰화 (모두 <0x80)
   ▼
process_cmd → strcmp(cmdlist[].cmdname, str[0])    ← byte-exact 매칭
```

### 1-1. 바이트 필터 (`accept_input`, io.c:461)

```c
if(buf[i] > 31 || ((buf[i]&0x80) && (unsigned char)buf[i]!=155) || ...
```

- (io.c:462) `buf`는 `char`(부호 있음). 고비트 바이트(0x80–0xFF)는 음수라 `> 31`이 거짓 → **둘째 절 `(buf[i]&0x80)`로 통과**한다. 즉 EUC-KR 선·후행 바이트는 전부 그대로 링버퍼에 들어간다.
- **유일한 예외: byte 155(0x9B = 단일바이트 CSI)** 를 필터링한다 — ANSI 이스케이프 주입 방어. (완성형 후행 바이트 범위 0xA1–0xFE에는 0x9B가 없으므로 한글은 영향 없음.)
- **telnet IAC(0xFF) 미처리 gap**: 0xFF는 `&0x80` 참 + ≠155라 그대로 적재된다. 이 계층에서 telnet 옵션 협상을 스트립하지 않는다. 라인모드 클라이언트에선 실무상 문제 없으나, 재구현 시 프로토콜 경계에서 명시 처리 대상.

### 1-2. read-safe / edit-unsafe 비대칭 (가장 날카로운 byte 처리 결함)

읽기·비교는 byte-투명성 덕에 한글에서 완벽히 동작하지만, **편집은 깨진다**:

```c
else if(buf[i] == '\b' && ihead != itail) {   io.c:468
    ihead--;          /* 무조건 1바이트만 뒤로 — 문자 경계 검사 없음 */
}
```

백스페이스 한 번이 **무조건 1바이트**를 지운다. 2바이트 한글을 지우려면 두 번 눌러야 하고, 한 번만 누르면 **선행 바이트만 남은 깨진 반쪽**이 입력에 잔류한다. 주석 처리된 `%`-doubling 코드(io.c:471, 484)는 과거 이 문제를 이스케이프로 우회하려던 흔적이다. 라인 편집은 byte-단위이지 character-단위가 아니다.

### 1-3. `lowercize`는 ASCII 한정 (misc.c:57)

```c
str[i] = (str[i] >= 'A' && str[i] <= 'Z') ? str[i]+32 : str[i];
```

`'A'`–`'Z'`만 +32한다. 고비트 한글 바이트는 이 범위 밖이라 **불변**. 따라서 한글 명령 토큰은 lowercize를 byte-safe하게 통과한다. (영문 별칭만 대소문자 정규화됨.)

## 2. 방향 매핑 — 콘텐츠(이식 대상)

### 2-1. 매핑표 (이식할 정본 어휘)

방향 입력은 **고정 별칭층 → 방향어 정규화 → 출구명 리터럴 매칭** 3단이다. 정규화는 `move()`(command2.c:338–345)에 인라인돼 있다:

| 입력 별칭 | 정규화 결과 | 의미 | 비고 |
|---|---|---|---|
| `2` / `ㄴ`(0xA4A4) | 남 | 남(south) | numpad↓ · 南 초성 |
| `4` / `ㅅ`(0xA4B5) | 서 | 서(west) | numpad← · 西 초성 |
| `6` / `ㄷ`(0xA4A7) | 동 | 동(east) | numpad→ · 東 초성 |
| `8` / `ㅂ`(0xA4B2) | 북 | 북(north) | numpad↑ · 北 초성 |
| `3` / `ㅁ`(0xA4B1) | 밑 | 아래(down) | numpad · 밑 초성 |
| `9` / `ㅇ`(0xA4B7) | 위 | 위(up) | numpad · 위 초성 |
| `나가` | 밖 | 바깥(out) | 명시 단어 |
| (그 외) | 입력 그대로 | 명명 출구 | `else strcpy(tempstr, str)` |

```c
     if(str[0]=='2' || !strcmp(str,"＂") || !strcmp(str,"ㄴ")) strcpy(tempstr, "남");
else if(str[0]=='4' || ...                || !strcmp(str,"ㅅ")) strcpy(tempstr, "서");
... (동/북/밑/위) ...
else if(!strcmp(str,"나가")) strcpy(tempstr, "밖");
else strcpy(tempstr, str);
/* 그 후: 방의 출구 리스트를 선형 탐색, xp->ext->name == tempstr 매칭 */
```

정규화된 `tempstr`는 방 데이터의 **출구명(`exit_->name`)** 과 byte-exact 비교된다. 즉 방향 어휘는 코드가 아니라 **월드 데이터(출구명)에 산다**. `data/world/rooms.json` 실측 분포(총 출구 5353 / 고유 출구명 291):

```
동:1034  서:1034  북:1025  남:1019  밖:240  위:129  밑:128
남서:41  북서:40  북동:40  남동:39
거실:29  문:27  입구:24  1번:20  승강기:16  막사:15  철문:12  침실:12  성문:10 …
```

`else` 폴스루 덕에 **명명 출구**(거실/문/입구/1번/승강기/철문 등 291종)는 별칭 없이 입력 그대로 출구명과 매칭된다 — 방향 어휘가 데이터 구동으로 무한 확장된다.

### 2-2. 대각선 방향 — 데이터엔 있으나 별칭 비활성 (결정 입력)

대각선 출구(남서/북서/북동/남동)는 데이터에 **약 160개 존재**한다. 그러나 numpad 조합(1/7/9/3)·jamo 조합(ㄴㅅ/ㅂㅅ 등) → 대각선 정규화 블록은 **전부 주석 처리**(command2.c:328–337)돼 라이브에서 비활성이다:

```c
/*
if(!strcmp(str,"ㄴㅅ") || ... || !strcmp(str,"24") || ... ) strcpy(tempstr, "남서");
...                                                            북서/남동/북동
else  */
```

→ 라이브 동작: 대각선 출구는 **전체 단어("남서" 등)를 직접 입력해야만** 도달한다. numpad 사선·jamo 조합 단축은 죽어 있다. **재구현 시 대각선 별칭 복원 여부를 결정**해야 한다(데이터엔 출구가 존재하므로 복원이 자연스러움).

### 2-3. `get_exit_char()`는 vestigial 중복 (han.c)

이슈는 `get_exit_char`를 방향 매퍼로 가정했으나, **실측 결과 호출자가 0개인 dead code**다. §2-1과 글자까지 같은 로직이 `move()`에 인라인 복제됐다 — 추상화가 채택되지 못하고 inline으로 굳은 흔적. 이식할 산출물은 dead 함수가 아니라 **매핑표 그 자체**(라이브 `move()`와 동일)다.
(주의: `han.c` 자체는 죽지 않았다 — 같은 파일의 `exam[]`·`johab_exam[]` 배열은 `first_han`이 쓴다. §3-2.)

### 2-4. `"＂"` 리터럴은 손상된 vestigial 상수

매핑 각 분기의 둘째 비교 `!strcmp(str,"＂")`는 실제 바이트가 **`c9 a5 a3 a2`** (EUC-KR 2문자: 0xC9A5 + 0xA3A2 전각따옴표)인 4바이트 mojibake이며, **7개 분기 전부 동일 문자열**이다. if/else-if 순차 평가 특성상 이 입력은 **언제나 첫 분기(남)에만 매칭**되고 나머지는 도달 불가능하다. 의미를 잃은 복붙 손상 상수로, 이식 대상이 아니다.

## 3. 조합형 변환(KStbl) — I/O가 아니라 언어 분석용

`kstbl.h`의 `KStbl[2350]`은 **완성형(EUC-KR) → 조합형(johab)** 룩업 테이블이다(2350 = 완성형 한글 글자 수). 그러나 **I/O 인코딩 변환에는 전혀 쓰이지 않는다**. 용도는 자모 추출 두 가지뿐이다. 인덱스 공식(command1.c:726, 748):

```c
KStbl[(high-0xb0)*94 + (low-0xa1)]   /* 94 = 0xFE-0xA1+1, 완성형 한 행의 글자 수 */
```

`is_hangul`(command1.c:703)이 선행 0xB0–0xC8 · 후행 0xA1–0xFE 범위로 한글을 판정한 뒤 조합형 코드를 뽑아 자모 비트필드를 마스킹한다.

### 3-1. `under_han` — 받침 추출 → 조사 선택 (**콘텐츠**)

```c
high = KStbl[...] & 0x1f;        /* 조합형 종성(받침) 코드 */
if(high<2 || high>28) return 0;  /* 받침 없음 → 0 */
return 1;                         /* 받침 있음 → 1 */
```

문자열 **마지막 한글의 받침 유무**를 반환한다. 이것은 보존해야 할 **언어 규칙**이다 — 한국어 조사가 앞 음절 받침에 따라 갈리기 때문. 출력측 조사 자동선택(§4)과 일부 메시지(creature.c:314 "…가지고 있던것")가 의존한다. 마지막 글자가 한글이 아니면(숫자/영문/한자) `is_hangul` 거짓 → **0 반환 → 개방형(는/가/를) 기본**. 재구현 유틸도 이 기본값을 똑같이 복제해야 충실하다.

### 3-2. `first_han` — 초성 추출 → 파일 버킷팅 (**형상**)

```c
high = (KStbl[...] >> 8) & 0x7c;  /* 조합형 초성 코드 */
for(i=0; johab_exam[i][0]; i++)
    if((johab_exam[i][0]&0x7f)==high) return exam[i];  /* 대표 음절 반환 */
```

문자열 **첫 한글의 초성**을 가나다 대표 음절(`exam[]`: 가·나·다·라·마·바·사…)로 매핑한다. 용도는 오로지 **플레이어 세이브 파일 경로 샤딩**: `PLAYERPATH/{초성}/{이름}` (files2.c:549·604, command1.c:89, post.c:50 등 다수). 이건 언어 규칙이 아니라 **파일시스템 디렉토리 분산 전략**이다 — MongoDB 신규 스택에선 **버리는 형상**이고, 조합형 테이블 자체를 이식할 필요가 없다.

## 4. 출력측 조사 자동선택 — 콘텐츠(규칙)

출력은 입력과 대칭으로 **raw EUC-KR byte를 그대로 write**한다(io.c:539 `scwrite(i, &Ply[i].io->output[otail], …)`) — 출력 방향도 인코딩 0회. 출력 i18n의 핵심은 **printf류 조사 보간**이다.

`io.c:604`의 테이블과 `%j` 포맷 지정자(io.c:672):

```c
char *Josa[6][2] = { {"은","는"},{"이","가"},{"과","와"},{"을","를"},{"으로","로"} };
/* %j<n> 처리: */
if(under_han(prestr)) arg[ind] = (int)Josa[digit][0];  /* 받침 O → 은/이/과/을/으로 */
else                  arg[ind] = (int)Josa[digit][1];  /* 받침 X → 는/가/와/를/로   */
```

포맷 문자열이 명사 출력(`%m`/`%s`) 뒤에 `%j0`~`%j4`를 두면, 런타임이 **앞 명사의 받침을 검사해 올바른 조사를 자동 선택**한다(인덱스 0=은/는, 1=이/가, 2=과/와, 3=을/를, 4=으로/로). 이 규칙(받침→조사 매핑)은 콘텐츠로 이식 대상이며, `under_han`(§3-1)에 직접 의존한다.

## 5. 콘텐츠(이식) vs 형상(재설계) 분류

| 항목 | 분류 | 이식/재설계 방침 |
|---|---|---|
| 방향 어휘(동서남북위밑밖 + 대각선) | 콘텐츠 | 명령 어휘 테이블로 이식. 출구명은 월드 데이터에서 그대로. |
| numpad/jamo → 방향 별칭 매핑(§2-1) | 콘텐츠 | 별칭 맵을 데이터/설정으로 이식. 대각선 별칭 복원 여부 결정(§2-2). |
| 조사 규칙(받침 → 은/이/을/과/으로)(§4) | 콘텐츠 | `Josa` 테이블 + 받침 판정 유틸로 재구현. |
| 받침 판정(`under_han`)(§3-1) | 콘텐츠 | 알고리즘 교체(KStbl → Unicode 산술), 동작 동일. |
| EUC-KR byte-투명 I/O(§1) | 형상 | UTF-8로 재설계. 변환은 `port/` 단계에서 1회. |
| 입력 링버퍼·라인 추출(§1-1) | 형상 | WebSocket 메시지 경계로 대체. |
| 백스페이스 byte 편집(§1-2) | 형상 | 클라이언트 IME/입력창이 character 단위 처리. |
| 초성 파일 샤딩(`first_han`)(§3-2) | 형상 | MongoDB 문서 저장으로 폐기. 조합형 테이블 미이식. |
| `get_exit_char`(§2-3)·`"＂"`(§2-4) | 폐기 | dead/손상 코드, 이식 안 함. |

## 6. 아키텍처 함의

### 6-1. i18n 경계: "어디서 변환하나" → 라이브에선 변환 없음

byte-투명성이 만든 EUC-KR 의존은 **신규 스택에서 소멸**한다. EUC-KR → UTF-8 변환은 **데이터 마이그레이션 시점(`port/`)에 단 한 번** 일어나며(이미 `port/`가 EUC-KR을 읽어 JSON으로 변환 중), 라이브 서버는 **UTF-8 전용**이다. WebSocket이 UTF-8 JSON을 나르므로 §1의 byte 처리 우려(반쪽 한글·CSI·IAC)는 **프로토콜 계층에서 사라진다**. → **i18n 변환 경계 = 오프라인 데이터 변환 1지점**, 런타임 경계 없음.

### 6-2. 받침/조사 규칙은 인코딩과 함께 사라지지 **않는다**

대비를 분명히: UTF-8 전환으로 *byte 처리* 문제는 없어지지만 *받침 → 조사 규칙*은 **그대로 살아 콘텐츠로 넘어간다**. `under_han`(KStbl 룩업)의 깔끔한 대체:

```ts
// 사전조합 한글 U+AC00–U+D7A3: 종성 인덱스 = (code-0xAC00) % 28, 0이면 받침 없음
function hasJongseong(s: string): boolean {
  const c = s.codePointAt(s.length - 1);
  if (c === undefined || c < 0xac00 || c > 0xd7a3) return false; // 비한글 → false(개방형)
  return (c - 0xac00) % 28 !== 0;
}
```

비한글 말미는 `false`(개방형 조사) — oracle 기본값과 일치시켜야 충실하다. 이 유틸 + `Josa` 테이블이 출력 조사 보간을 재현한다(서버 렌더 또는 클라이언트 i18n 중 택1 — 구조화 JSON이면 클라이언트 렌더가 자연스러움).

### 6-3. 명령 토크나이저: byte → character 경계 상승

A2가 다룬 한국어 **동사-후치 파싱**(마지막 토큰 = 동사)은 그대로 이식하되, UTF-8에선 토큰화가 **byte-단위에서 character-단위로 상승**해 §1-2의 반쪽-한글 위험이 원천 제거된다. 공백/문장부호 구분자 의미론은 동일하게 보존한다.

### 6-4. 방향 처리 = 어휘 테이블 + 별칭 맵 + 출구명 데이터

방향은 (a) 정규화 별칭 맵(numpad/jamo → 방향어), (b) 출구명 리터럴 매칭 두 층으로 재구현한다. `move()` 인라인 중복(§2-3)은 단일 매핑 모듈로 정규화한다. **대각선 별칭 복원**(§2-2)은 명시적 결정 항목 — 데이터엔 대각선 출구가 존재하므로 복원이 합리적이다.
