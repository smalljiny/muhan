# A3 한글 입출력·방향 매핑

> 무한이 한글 입출력, 방향 매핑, 인코딩을 어디서 어떻게 처리하는지 오라클에서 정리한다. 서버의 i18n 경계를 정하고 명령 토크나이저를 설계할 때 참고한다. 이슈 #3. 출처는 `legacy/muhan/src`(EUC-KR, byte-level)이며, 코드를 이식하지 않고 동작만 추출한다.

## 개요

무한의 한글 처리 전체에 걸쳐 성립하는 **불변식은 하나뿐이다.** "EUC-KR은 ASCII-투명(byte-transparent)"하다는 것이다. 서버는 한글을 디코딩하지 않는다. 입력은 raw byte 그대로 링버퍼에 쌓인다. 명령, 출구, 대상을 매칭할 때는 모두 byte-exact `strcmp`를 쓴다. 출력도 raw byte를 그대로 내보낸다. 따라서 "인코딩 처리 경계"는 사실상 없고, 게임 전체가 하나의 바이트열 공간에서 동작한다.

이 byte-투명성은 EUC-KR 완성형 한글이 항상 고비트 바이트 쌍으로만 표현되기 때문에 성립한다(`is_hangul`: 선행 0xB0–0xC8, 후행 0xA1–0xFE). ASCII 구분자(공백 0x20, `#` 0x23, 문장부호 `.`/`!`/`?`)는 모두 < 0x80이라 **2바이트 한글 사이에 끼어들 수 없다**. 그래서 바이트 단위로 짠 토크나이저와 비교 코드가 한글에서도 그대로 옳게 동작한다.

핵심 발견 6가지:

| # | 발견 | 성격 |
|---|------|------|
| 1 | **인코딩 경계 없음** — 입출력 양방향 raw EUC-KR byte, 디코딩 0회 | 재설계 |
| 2 | **방향 매핑은 `move()`에 인라인** — `get_exit_char()`(han.c)는 호출자 0의 dead code, 동일 로직이 `command2.c`에 복제됨 | 이식(매핑표) + 재설계(중복 제거) |
| 3 | **조합형 변환(KStbl)은 I/O가 아니라 언어 분석용** — 받침 추출(조사 선택)·초성 추출(파일 버킷팅) 두 용도뿐, 완성형↔조합형 I/O 변환은 없음 | 분기(아래 §3) |
| 4 | **출력측 조사(josa) 자동선택** — `%j` 포맷 + `Josa[6][2]` 테이블 + 받침 검사 | 이식(규칙) |
| 5 | **대각선 방향은 데이터에 존재하나 numpad/jamo 별칭은 비활성**(주석 처리) — 전체 단어 입력으로만 도달 | 이식(커스텀 단축키 기본값으로 흡수 예정) |
| 6 | **백스페이스는 바이트 단위** — 2바이트 한글의 반쪽만 삭제하는 read-safe / edit-unsafe 비대칭 | 재설계(클라이언트로 이관) |

## 1. 입력 바이트 경로 — 불변식의 실제 동작

입력 한 줄의 수명: 소켓 → 링버퍼 → 라인 추출 → 토큰화 → 디스패치.

```
read(fd, buf, 127)                 io.c:451   ← raw byte, 디코딩 없음
   │  · byte filter (아래)
   ▼
Ply[fd].io->input[] (ring buffer)  io.c:481   ← byte 단위 로드, CR/LF에 commands++
   ▼
server_loop가 라인 1줄 추출         io.c:792   (13/10 = 라인 종결)
   ▼
command(fd, param, str)            command1.c:415
   │  · lowercize(str, 0)          ← ASCII 'A'–'Z'만 소문자화, 한글 byte 무영향
   ▼
parse(str, &cmnd)                  command1.c:505   ← 공백/`#`/문장부호로 토큰화 (모두 <0x80)
   ▼
process_cmd → strcmp(cmdlist[].cmdname, str[0])    ← byte-exact 매칭
```

### 1-1. 바이트 필터 (`accept_input`, io.c:461)

```c
if(buf[i] > 31 || ((buf[i]&0x80) && (unsigned char)buf[i]!=155) || ...
```

- (io.c:462) `buf`는 부호 있는 `char`다. 고비트 바이트(0x80–0xFF)는 음수라서 `> 31`이 거짓이 되고, 대신 **둘째 절 `(buf[i]&0x80)`로 통과**한다. 즉 EUC-KR 선행·후행 바이트는 전부 그대로 링버퍼에 들어간다.
- **유일한 예외:** byte 155(0x9B = 단일바이트 CSI)는 걸러 낸다. ANSI 이스케이프 주입을 막기 위해서다. 완성형 후행 바이트 범위 0xA1–0xFE에는 0x9B가 없으므로 한글은 영향을 받지 않는다.
- **telnet IAC(0xFF) 미처리 gap:** 0xFF는 `&0x80`이 참이고 155가 아니므로 그대로 로드된다. 이 계층은 telnet 옵션 협상을 걸러 내지 않는다. 라인모드 클라이언트에서는 실무상 문제가 없지만, 재구현할 때는 프로토콜 경계에서 명시적으로 처리해야 한다.

### 1-2. read-safe / edit-unsafe 비대칭 (가장 날카로운 byte 처리 결함)

읽기와 비교는 byte-투명성 덕분에 한글에서도 완벽히 동작하지만, **편집은 깨진다**.

```c
else if(buf[i] == '\b' && ihead != itail) {   io.c:468
    ihead--;          /* 무조건 1바이트만 뒤로 — 문자 경계 검사 없음 */
}
```

백스페이스는 한 번에 무조건 1바이트를 지운다. 2바이트 한글을 지우려면 두 번 눌러야 한다. 한 번만 누르면 **선행 바이트만 남은 깨진 반쪽**이 입력에 남는다. 주석 처리된 `%`-doubling 코드(io.c:471, 484)는 예전에 이 문제를 이스케이프로 우회하려던 흔적이다. 라인 편집은 character 단위가 아니라 byte 단위로 이뤄진다.

### 1-3. `lowercize`는 ASCII 한정 (misc.c:57)

```c
str[i] = (str[i] >= 'A' && str[i] <= 'Z') ? str[i]+32 : str[i];
```

`'A'`–`'Z'`에만 32를 더한다. 고비트 한글 바이트는 이 범위 밖이라 **바뀌지 않는다**. 따라서 한글 명령 토큰은 lowercize를 byte-safe하게 통과하고, 대소문자 정규화는 영문 별칭에만 적용된다.

## 2. 방향 매핑 — 콘텐츠(이식 대상)

### 2-1. 매핑표 (이식할 기준 어휘)

방향 입력은 **고정 별칭층 → 방향어 정규화 → 출구명 리터럴 매칭**의 3단계로 처리된다. 정규화 코드는 `move()`(command2.c:338–345) 안에 인라인으로 들어 있다.

| 입력 별칭 | 정규화 결과 | 의미 | 비고 |
|---|---|---|---|
| `2` / `ㄴ`(0xA4A4) | 남 | 남(south) | numpad↓ · 南 초성 |
| `4` / `ㅅ`(0xA4B5) | 서 | 서(west) | numpad← · 西 초성 |
| `6` / `ㄷ`(0xA4A7) | 동 | 동(east) | numpad→ · 東 초성 |
| `8` / `ㅂ`(0xA4B2) | 북 | 북(north) | numpad↑ · 北 초성 |
| `3` / `ㅁ`(0xA4B1) | 밑 | 아래(down) | numpad · 밑 초성 |
| `9` / `ㅇ`(0xA4B7) | 위 | 위(up) | numpad · 위 초성 |
| `나가` | 밖 | 바깥(out) | 명시 단어 |
| (그 외) | 입력 그대로 | 명명 출구 | `else strcpy(tempstr, str)` |

```c
     if(str[0]=='2' || !strcmp(str,"＂") || !strcmp(str,"ㄴ")) strcpy(tempstr, "남");
else if(str[0]=='4' || ...                || !strcmp(str,"ㅅ")) strcpy(tempstr, "서");
... (동/북/밑/위) ...
else if(!strcmp(str,"나가")) strcpy(tempstr, "밖");
else strcpy(tempstr, str);
/* 그 후: 방의 출구 리스트를 선형 탐색, xp->ext->name == tempstr 매칭 */
```

정규화된 `tempstr`는 방 데이터의 출구명(`exit_->name`)과 byte-exact로 비교된다. 즉 방향 어휘는 코드가 아니라 **월드 데이터의 출구명에 정의된다**. 아래는 `data/world/rooms.json`에서 실측한 분포다(총 출구 5353 / 고유 출구명 291).

```
동:1034  서:1034  북:1025  남:1019  밖:240  위:129  밑:128
남서:41  북서:40  북동:40  남동:39
거실:29  문:27  입구:24  1번:20  승강기:16  막사:15  철문:12  침실:12  성문:10 …
```

`else` 폴스루 덕분에 **명명 출구**(거실/문/입구/1번/승강기/철문 등 291종)는 별칭 없이 입력 그대로 출구명과 매칭된다. 그래서 데이터만 추가하면 방향 어휘를 얼마든지 늘릴 수 있다.

### 2-2. 대각선 방향 — 데이터엔 있으나 별칭 비활성 (결정 입력)

대각선 출구(남서/북서/북동/남동)는 데이터에 약 160개 있다. 그러나 numpad 조합(1/7/9/3)이나 jamo 조합(ㄴㅅ/ㅂㅅ 등)을 대각선으로 정규화하는 블록은 **전부 주석 처리**(command2.c:328–337)돼 있어 라이브에서는 동작하지 않는다.

```c
/*
if(!strcmp(str,"ㄴㅅ") || ... || !strcmp(str,"24") || ... ) strcpy(tempstr, "남서");
...                                                            북서/남동/북동
else  */
```

→ 라이브 동작: 대각선 출구에는 **"남서" 같은 전체 단어를 직접 입력해야만** 갈 수 있다. numpad 사선 입력과 jamo 조합 단축은 동작하지 않는다.

> **계획 메모(미확정)**: 대각선 별칭을 하드코딩으로 되살리지 않는다. 대신 향후 계획 중인 **사용자 명령어 커스텀 단축키 기능**의 기본 프리셋 값에 방향 별칭(numpad/jamo/대각선)을 넣고, 사용자가 다시 정의할 수 있게 한다. 이 기능은 플레이어가 임의 명령에 단축키를 지정하는 기능이다. 즉 §2-1의 인라인 정규화층 전체를 별도 매핑으로 두지 않고 alias 시스템의 기본값으로 일반화한다. 구체적인 범위와 스키마는 명령 파서/alias 구현 토픽에서 확정한다.

### 2-3. `get_exit_char()`는 vestigial 중복 (han.c)

이슈는 `get_exit_char`를 방향 매퍼로 가정했다. 그러나 실측해 보니 **호출자가 0개인 dead code**다. §2-1과 글자까지 같은 로직이 `move()`에 인라인으로 복제돼 있다. 추상화를 만들었지만 쓰이지 않고 인라인 코드가 그대로 남은 흔적이다. 이식할 산출물은 dead 함수가 아니라 **매핑표 자체**이며, 이는 라이브 `move()`의 매핑과 같다.
(주의: `han.c` 파일 자체가 죽은 것은 아니다. 같은 파일의 `exam[]`·`johab_exam[]` 배열은 `first_han`이 쓴다. §3-2 참고.)

### 2-4. `"＂"` 리터럴은 손상된 vestigial 상수

매핑의 각 분기에 있는 둘째 비교 `!strcmp(str,"＂")`는 실제 바이트가 **`c9 a5 a3 a2`**인 4바이트 mojibake다. EUC-KR 2문자(0xC9A5 + 0xA3A2 전각따옴표)에 해당하며, 7개 분기 모두 같은 문자열이다. if/else-if는 순서대로 평가되므로 이 입력은 **언제나 첫 분기(남)에만 매칭**되고 나머지 분기에는 도달하지 못한다. 복사·붙여넣기 중 손상돼 의미를 잃은 상수이므로 이식하지 않는다.

## 3. 조합형 변환(KStbl) — I/O가 아니라 언어 분석용

`kstbl.h`의 `KStbl[2350]`은 완성형(EUC-KR)을 조합형(johab)으로 바꾸는 룩업 테이블이다(2350 = 완성형 한글 글자 수). 그러나 **I/O 인코딩 변환에는 전혀 쓰이지 않고**, 자모를 추출하는 두 가지 용도로만 쓰인다. 인덱스 공식은 다음과 같다(command1.c:726, 748).

```c
KStbl[(high-0xb0)*94 + (low-0xa1)]   /* 94 = 0xFE-0xA1+1, 완성형 한 행의 글자 수 */
```

먼저 `is_hangul`(command1.c:703)이 선행 0xB0–0xC8, 후행 0xA1–0xFE 범위로 한글인지 판정한다. 그다음 조합형 코드를 구해 자모 비트필드를 마스킹한다.

### 3-1. `under_han` — 받침 추출 → 조사 선택 (**콘텐츠**)

```c
high = KStbl[...] & 0x1f;        /* 조합형 종성(받침) 코드 */
if(high<2 || high>28) return 0;  /* 받침 없음 → 0 */
return 1;                         /* 받침 있음 → 1 */
```

문자열 마지막 한글에 받침이 있는지를 반환한다. 한국어 조사는 앞 음절의 받침에 따라 달라지므로, 이 함수는 보존해야 할 **언어 규칙**이다. 출력측 조사 자동선택(§4)과 일부 메시지(creature.c:314 "…가지고 있던것")가 이 함수를 쓴다. 마지막 글자가 숫자, 영문, 한자처럼 한글이 아니면 `is_hangul`이 거짓이 되어 0을 반환한다. 그러면 **받침 없는 형태(는/가/를)가 기본**으로 쓰인다. 재구현할 유틸도 이 기본값을 똑같이 따라야 원본과 같게 동작한다.

### 3-2. `first_han` — 초성 추출 → 파일 버킷팅 (**구현 방식**)

```c
high = (KStbl[...] >> 8) & 0x7c;  /* 조합형 초성 코드 */
for(i=0; johab_exam[i][0]; i++)
    if((johab_exam[i][0]&0x7f)==high) return exam[i];  /* 대표 음절 반환 */
```

문자열 첫 한글의 초성을 가나다 대표 음절(`exam[]`: 가·나·다·라·마·바·사…)로 매핑한다. 용도는 **플레이어 세이브 파일 경로 샤딩** 하나뿐이다. 경로는 `PLAYERPATH/{초성}/{이름}` 형태다(files2.c:549·604, command1.c:89, post.c:50 등 다수). 이것은 언어 규칙이 아니라 파일시스템 디렉토리를 분산하는 전략이다. MongoDB를 쓰는 신규 스택에서는 **버리는 구현 방식**이고, 조합형 테이블 자체도 이식할 필요가 없다.

## 4. 출력측 조사 자동선택 — 콘텐츠(규칙)

출력도 입력과 마찬가지로 raw EUC-KR byte를 그대로 write한다(io.c:539 `scwrite(i, &Ply[i].io->output[otail], …)`). 출력 방향에서도 인코딩 변환은 0회다. 출력 i18n의 핵심은 **printf류 조사 보간**이다.

아래는 `io.c:604`의 테이블과 `%j` 포맷 지정자(io.c:672) 처리다.

```c
char *Josa[6][2] = { {"은","는"},{"이","가"},{"과","와"},{"을","를"},{"으로","로"} };
/* %j<n> 처리: */
if(under_han(prestr)) arg[ind] = (int)Josa[digit][0];  /* 받침 O → 은/이/과/을/으로 */
else                  arg[ind] = (int)Josa[digit][1];  /* 받침 X → 는/가/와/를/로   */
```

포맷 문자열에서 명사 출력(`%m`/`%s`) 뒤에 `%j0`~`%j4`를 두면, 런타임이 **앞 명사의 받침을 검사해 맞는 조사를 자동으로 고른다**. 인덱스는 0=은/는, 1=이/가, 2=과/와, 3=을/를, 4=으로/로다. 이 받침→조사 매핑 규칙은 콘텐츠로 이식하며, `under_han`(§3-1)을 직접 사용한다.

## 5. 콘텐츠(이식) vs 구현 방식(재설계) 분류

| 항목 | 분류 | 이식/재설계 방침 |

## 6. 아키텍처 시사점

### 6-1. i18n 경계: "어디서 변환하나" → 라이브에선 변환 없음

byte-투명성 때문에 생긴 EUC-KR 의존은 신규 스택에서 없어진다. EUC-KR → UTF-8 변환은 **데이터 마이그레이션 시점(`port/`)에 단 한 번** 일어난다. 이미 `port/`가 EUC-KR을 읽어 JSON으로 변환하고 있다. 라이브 서버는 UTF-8만 쓴다. WebSocket이 UTF-8 JSON을 전달하므로, §1에서 본 byte 처리 문제(반쪽 한글, CSI, IAC)는 프로토콜 계층에서 생기지 않는다. → **i18n 변환 경계는 오프라인 데이터 변환 1곳뿐**이고, 런타임 경계는 없다.

### 6-2. 받침/조사 규칙은 인코딩과 함께 사라지지 **않는다**

둘을 구분해야 한다. UTF-8로 바꾸면 *byte 처리* 문제는 없어지지만, *받침 → 조사 규칙*은 **그대로 남아 콘텐츠로 넘어간다**. `under_han`(KStbl 룩업)은 다음처럼 간단히 대체할 수 있다.

```ts
// 사전조합 한글 U+AC00–U+D7A3: 종성 인덱스 = (code-0xAC00) % 28, 0이면 받침 없음
function hasJongseong(s: string): boolean {
  const c = s.codePointAt(s.length - 1);
  if (c === undefined || c < 0xac00 || c > 0xd7a3) return false; // 비한글 → false(받침 없는 형태)
  return (c - 0xac00) % 28 !== 0;
}
```

끝 글자가 한글이 아니면 `false`(받침 없는 형태의 조사)를 반환한다. 오라클 기본값과 맞춰야 원본과 같게 동작하기 때문이다. 실제 한국어에서는 숫자나 영문으로 끝나는 말을 발음에 따라 처리한다("3은"=삼→ㅁ받침). 하지만 오라클은 모두 받침 없는 형태로 처리하므로, **동작 재현 원칙에 따라 포팅도 이 단순화를 그대로 이식**한다.

**`으로/로`의 ㄹ 예외 — 오라클 버그(이식 시 결정 항목)**: `under_han`은 받침이 *있는지*만 0/1로 반환한다(io.c:679). 그래서 `Josa[4]={으로,로}`에서 ㄹ받침도 "받침 있음→으로"로 처리되어 "칼으로"가 나온다(틀림, 정답은 "칼로"). 다른 조사(은/는·이/가·을/를·과/와)는 받침 유무만 보면 되므로 정상이다. **`으로/로`만 ㄹ 예외가 필요**한데 오라클은 이를 빠뜨렸다. → 재구현 때 정할 것: (a) 버그까지 그대로 이식할지, (b) `종성==8(ㄹ)`이면 `로`를 쓰는 예외를 추가할지. 비용이 적은 개선이라 (b)를 권하지만 판단이 필요하다.

**조사 렌더 위치**: 이 유틸과 `Josa` 테이블로 출력 조사 보간을 재현한다. 오라클에서는 서버가 `%j` 포맷으로 조사를 직접 넣는다(§4). 하지만 구조화 JSON 프로토콜에서는 **서버가 명사와 조사 슬롯 코드만 보내고, 클라이언트 i18n 레이어가 받침 검사와 조사 렌더를 맡는** 편이 자연스럽다. 렌더링 관심사를 표현 계층으로 분리할 수 있기 때문이다. 서버에서 렌더해도 되지만, 클라이언트로 분리하는 편이 다국어와 테마를 확장하기에 유리하다.

### 6-3. 명령 토크나이저: byte → character 경계 상승

A2가 다룬 한국어 **동사-후치 파싱**(마지막 토큰 = 동사)은 그대로 이식한다. 다만 UTF-8에서는 토큰화 단위가 **byte에서 character로 올라가므로** §1-2의 반쪽 한글 문제가 아예 생기지 않는다. 공백과 문장부호를 구분자로 쓰는 방식은 그대로 유지한다.

### 6-4. 방향 처리 = 어휘 테이블 + 별칭 맵 + 출구명 데이터

방향은 두 층으로 재구현한다. (a) 정규화 별칭 맵(numpad/jamo → 방향어), (b) 출구명 리터럴 매칭이다. `move()`에 인라인으로 중복된 코드(§2-3)는 하나의 매핑 모듈로 정리한다. **방향 별칭층(a)은 향후 사용자 명령어 커스텀 단축키 기능의 기본값으로 옮길 수 있다**(§2-2 계획 메모). 비활성 대각선 별칭도 따로 되살리지 말고 그 기본 프리셋에 포함하면 된다. 구체적인 내용은 명령 파서/alias 토픽에서 정한다.
