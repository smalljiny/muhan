# 무한 MUD → Node.js/웹 포팅 진행사항

> 작성일: 2026-06-25
> 대상: `legacy/muhan` (Mordor 파생 한국어 텔넷 MUD)를 Node.js 서버 + 구조화된 웹 UI로 재구현

---

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 원본 | **Mordor** MUD (Brett J. Vickers, 1991–93)의 한국어 파생본 "무한" |
| 언어/구조 | C, 32비트(`-m32`), `fork()` + `select` 루프, 플레이어별 `iobuf` |
| 인코딩 | **EUC-KR(완성형)** + 조합형(Johab) 변환 테이블(`kstbl.h`, `han.c`) |
| 목표 | Node.js 서버로 재구현 → 구조화된 웹 UI로 사용성 개선 |

### 합의된 아키텍처 방향
- **라이브 게임 상태는 Node 프로세스 메모리의 객체 그래프**에 둔다(원본 `Rom[]`/linked list처럼). DB를 게임 루프에서 왕복하지 않는다.
- **MongoDB** = 영속화(월드 정의·플레이어 세이브·게시판). 문서 모델이 원본 고정배열 구조체보다 더 잘 맞음.
- **Redis** = 나중에 도입(pub/sub 기반 `broadcast_rom` 대체, 세션, 멀티프로세스 확장 시). 초기 단일 프로세스는 in-memory `Map`+`EventEmitter`로 충분.
- **TypeScript** 기본.
- UX: **구조화된 웹 UI**(서버가 JSON 이벤트 송신). 지도는 3단계 — ① 나침반/클릭 출구 패널 → ② 좌표 자동지도(automap, 방향 출구 기반 BFS 격자) → ③ 존별 손그림(후순위).

## 2. 데이터 포맷 역설계 (완료)

원본 디스크 포맷 = **1993년 32비트 raw 구조체 덤프**. 32비트 ABI: `long`=4B, 포인터=4B, 정수 LE.

### 확정된 구조체 크기 (i386/alpine Docker로 `sizeof`/`offsetof` 추출 — ground truth)
| 구조체 | 크기 |
|---|---|
| `room` | 480 B |
| `exit_` | 44 B (name[20], room@20, flags@22, key@40) |
| `object` | 352 B |
| `creature` | 1184 B |
| `lasttime` | 12 B |

### 파일별 포맷
- **방** (`rooms/r{N/1000}/r{N:05d}`): `room`(480) + [int 출구수 + `exit_`×n] + [int 몬스터수 + `creature`각(1184+int invcnt+obj들)] + [int 아이템수 + `object`각(352+int cnt+중첩)] + [int len+short_desc][int len+long_desc][int len+obj_desc]. **비압축.**
- **아이템 템플릿** (`objmon/o##`): `object` 100개 평면배열(352B씩), `lseek(idx*352)`.
- **몬스터 템플릿** (`objmon/m##`): `creature` 100개 평면배열(1184B씩).
- **플레이어 세이브** (`player/`): `creature` 구조체 덤프를 **LZW 압축**(`src/compress.c`). ← **아직 미해독**
- **텍스트** (`help/`, `post/`, objmon 특수오브젝트): 평문 EUC-KR(CRLF).

### 직렬화 코드 위치
- `src/files1.c`: `read_rom`/`write_rom`/`read_crt`/`write_crt`/`read_obj`/`write_obj` (파일이 EUC-KR이라 grep 전 `iconv` 필요)
- `src/files2.c`: `load_rom`/`load_crt`/`load_obj` (경로 공식)
- `src/files3.c`: `*_to_mem`/`*_from_mem` (메모리 직렬화 버전)

### 중요 발견: 방 ID와 orphan
- 원본 로드 공식(`files2.c`): `sprintf(file, "%s/r%02d/r%05d", ROOMPATH, index/1000, index)`
- → **방의 진짜 ID = 로드 경로의 번호**. 구조체 내부 `rom_num` 필드는 stale일 수 있음(예: `r09000`의 내부값=0).
- → 디렉터리가 `N/1000`과 안 맞는 파일은 **게임이 절대 로드 못 하는 orphan**(백업/구버전).
- 전체 방파일 **3216개 = 정본 2341개 + orphan 875개**(내용 전부 다름, 무시).

## 3. 검증 (완료)

### 방 파서 (`port/parseRoom.js`)
- 방파일 3216개 중 **3209개(99.8%) `leftover=0` 완벽 파싱**, 예외 0.
- `leftover=0` = 구조체 크기·중첩·문자열 프레이밍이 끝까지 정확함을 의미(설명은 파일 맨 끝에 기록되므로 강한 증거).
- 실패 7건은 non-truncate 덮어쓰기 **잔여 tail**일 뿐 데이터 온전(설명·출구 정상 디코딩).

### 필드 오프셋 oracle 검증 (`port/templates.js`)
- **C oracle**(원본 `mstruct.h` 그대로 `#include`, i386/alpine 32비트 컴파일)이 같은 바이트를 구조체로 읽어 전 필드 출력 → JS 파서 출력과 diff.
- **결과: object 907개 + creature 1049개, 모든 필드 바이트 단위 완전 일치.**
- 의미론 sanity: `type` 코드가 `help/otypes`(Sharp0..Money10)와 정확히 일치, 스탯/금화/경험치 합리적.
- → 전투 스탯(hp/AC/thaco/level/주사위), 경제(value/gold/exp), 마법(realm/spells), 아이템 속성까지 신뢰 가능한 오프셋 확정.

### 인코딩
- 전체 설명문 40만 글자 중 U+FFFD 12개(99.997% 순수 EUC-KR). 디스크는 EUC-KR 확정.

## 4. 월드 → JSON 변환 (완료)

`port/convertWorld.js` (경로기준 정본만 선택, 멱등). 산출: `data/world/`

```
data/world/
├── rooms/              2,341개 (r00000.json ~)  — 개별 편집/git diff용 정본
├── rooms.json          2.4 MB  (번들 배열)        — 부팅 로드/Mongo insertMany용
├── objects.json        212 KB  (아이템 709개)
├── creatures.json      340 KB  (몬스터 674개)
└── meta.json           (개수·인코딩·노트)
```

### 규모 (minified UTF-8)
| 항목 | 개수 | 크기 | gzip |
|---|---:|---:|---:|
| 방 | 2,341 | 2.35 MB | 0.29 MB |
| 아이템 템플릿 | 709 | 0.21 MB | 26 KB |
| 몬스터 템플릿 | 674 | 0.33 MB | 56 KB |
| **합계** | | **≈ 2.9 MB** | **≈ 0.37 MB** |

(per-file 저장 시 디스크 ~9.9 MB — 4KB 블록 오버헤드. pretty는 ~4.4 MB.)

### 참조 무결성
- 출구 5353개 중 **99.8%가 실존 방을 가리킴**. 끊긴 출구 12개(0.2%)는 대부분 `사생십이관문 죽음의 문` 등 의도된 죽음/막다른 길로 추정.

### 미반영(텍스트 자산)
- `help/` 944 KB(232파일), `post/` 8 KB, objmon 특수오브젝트 본문 166개(보드/스크롤), `player/` 84 KB(21개, LZW).

| `port/parseRoom.js` | 방 파서(출구/몬스터/아이템/설명) + CLI |
