## Executive Summary

권위 상태를 프로세스 메모리에 두고 MongoDB에 영속화하는 서버의 기준 패턴은 **dirty-flag 기반 write-behind(write-back)** 이다. 라이브 틱은 인메모리 상태만 바꾸고, 바뀐 부분을 dirty로 표시한다. 내구성은 세 가지로 확보한다. (a) 주기 타이머로 flush하고, (b) 중요 이벤트(레벨업, 거래, 로그아웃)는 바로 write하며, (c) 종료할 때 강제로 flush한다 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/), [layrs.me](https://layrs.me/course/hld/07-caching/write-behind/), [LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md)). MMO 아키텍처의 통설은 "인메모리 월드 상태가 진짜 source of truth이고 DB는 복구용 영속화"라는 것이다. 이는 단일 프로세스 객체 그래프에 DB 네이티브 세이브를 더하는 본 프로젝트의 결정과 정확히 일치한다 ([PRDeving](https://prdeving.wordpress.com/2023/09/29/mmo-architecture-source-of-truth-dataflows-i-o-bottlenecks-and-how-to-solve-them/)). 경제와 은행의 무결성은 MongoDB 다중 문서 트랜잭션(`withTransaction`)이나 단일 문서 조건부 `findOneAndUpdate`+`$inc`로 지킨다. 두 방법 모두 원자성, 비음수, 멱등을 함께 보장한다 ([MongoDB Docs](https://www.mongodb.com/docs/manual/core/transactions/), [Franck Pachot](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)). 가장 잘 문서화된 함정은 **write-behind에서 flush 전에 크래시나 종료가 일어나 최근 변경이 사라지는 것**이다(Orleans 실사례). 완화책은 deactivate/shutdown 훅에서 강제로 flush하고 멱등 upsert를 쓰는 것이다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)).

## 1. Dirty-flag 주기 flush + 이벤트 즉시 write

**핵심 워크플로우.** 엔티티마다 인메모리 버퍼가 있고, 값이 바뀌면 해당 필드를 dirty로 표시한다. 주기 tick(alarm)은 dirty 필드만 기준 저장소에 쓰고 dirty 플래그를 지운다. 필드 단위로 dirty를 추적하면 write amplification이 줄어든다 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/)). 게임 세이브의 정설은 game state를 통째로 blob으로 쓰지 않는 것이다. (1) 정말 중요한 부분만, (2) 마지막 저장 이후 바뀐 것만, (3) 개별적으로 저장한다 ([gamedev.SE - periodically saving](https://gamedev.stackexchange.com/questions/31944/best-practices-for-periodically-saving-game-state-to-disk)).

**MUD 직접 선례.** LuminariMUD는 pulse 기반 메인 루프에서 `PULSE_AUTOSAVE`로 매 분마다 `Crash_save_all()`을 호출해 플레이어 데이터를 주기적으로 영속화한다. 종료 시퀀스에서도 저장한다. 레벨업 같은 중요 이벤트는 autosave 경로나 직접 save 호출로 바로 반영하도록 확장할 수 있다고 적혀 있다 ([LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md)). 다른 MUD 논의는 핵심 캐릭터 데이터(아이템, 스킬, 진행도)를 주기적으로 저장하라고 권한다. 그리고 **레벨업, 영역 이동, 보스 처치, 상점 이탈, 로그아웃/연결 끊김 때는 바로 저장**하라고 한다. 다만 매 틱마다 모든 NPC 위치를 저장하지는 말라고 한다 ([gamedev.SE - how often to save](https://gamedev.stackexchange.com/questions/19338/how-often-to-save-players-state-in-persistent-online-games)). 단일 플레이어 AI-MUD에는 "매 공격 틱마다 zone 상태 저장" 규칙이 있다. 히트 사이에 오래된 상태를 다시 읽어 몹 HP가 회복되는 버그를 막으려는 것이다. **저장 시점을 놓치면 실제 게임 버그가 된다**는 사례다 ([SINGLE-PLAYER-AI-MUD](https://github.com/undergroundrap/SINGLE-PLAYER-AI-MUD)).

**Flush 간격과 write coalescing의 트레이드오프.** 시간 기반 배칭(예: 5초/1분)은 DB 부하를 예측할 수 있다. 하지만 데이터가 최대 한 interval 동안 캐시에 머문다 ([layrs.me](https://layrs.me/course/hld/07-caching/write-behind/)). count 기반 flush(dirty 개수가 임계를 넘으면 flush)는 메모리 압력을 제한하며, 보통 interval 기반과 함께 쓴다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)). **write coalescing**은 같은 엔티티+컴포넌트에 쌓인 여러 pending write를 최신값 하나로 합친다(dedup). 예를 들어 60fps 드래그로 생긴 ~300개 transform 업데이트가 write 하나로 합쳐진다(last-write-wins) ([marathon RFC 0002](https://github.com/r3t-studios/marathon/blob/HEAD/docs/rfcs/0002-persistence-strategy.md), [techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)). 실제 SQL.js 프로젝트 하나는 고정 60초 interval autosave를 dirty-flag + 60초 debounce로 바꿨다. 그 결과 idle 상태에서는 write가 0이 되면서도 최대 staleness는 같은 60초로 유지했다 ([SeekerClaw PR#347](https://github.com/sepivip/SeekerClaw/pull/347)). Roblox용 오픈소스 Lyra는 lock-backed 세션마다 non-yielding 백그라운드 autosave 루프를 돌리고, shutdown 때 마지막으로 저장한다 ([Lyra Session](https://github.com/paradoxum-games/lyra/blob/e40d12a8/src/Session.luau)).

**간격 권장(판단이며, 소스는 단일값이 아니라 범위를 제시한다).** 소스들은 5초에서 수분까지 폭넓게 제시하며 정답은 하나가 아니다. 본 프로젝트(1Hz 틱, 소규모 동접)에서는 **60–300초 주기 flush와 중요 이벤트 즉시 write**를 함께 쓰는 것이 합리적인 출발점이다. 이는 원본 무한/Mordor의 분 단위 autosave 감각(LuminariMUD는 매분)과도 맞는다.

## 2. Snapshot→queue→async worker 파이프 + 백업-쓰기-교체 내구성

**틱 루프와 I/O의 분리.** 스토리지 I/O 지연이 메인 게임 루프(물리, 플레이어 추적, TPS)를 막지 않게 해야 한다. 그래서 메인 스레드는 DB 커맨드를 보내기만 하고 결과를 기다리지 않는다. 모든 DB I/O는 백그라운드 워커가 처리하고, 끝나면 콜백이나 이벤트로 메인 루프에 반영한다 ([mygamehost](https://mygamehost.net/en/wiki/synchronous-vs-asynchronous-how-databases-dictate-game-tps-stability)). 이는 고전적인 **Event Queue 패턴**이다. 생산자(게임 로직)가 write 이벤트를 큐에 넣으면, 별도 워커가 큐를 비우며 I/O를 수행하므로 프레임이 막히지 않는다 ([Game Programming Patterns - Event Queue](https://gameprogrammingpatterns.com/event-queue.html), [Socratopia](https://www.socratopia.app/library/game-code-anatomy-en/chapter-15)). Write Offloading에서는 게임 서버가 버퍼나 큐에 넣은 뒤 빠르게 ACK(1–5ms)하고, 워커가 감당할 수 있는 속도로 배치 write한다. 세션 단위로 파티셔닝해 순서를 지키고, **멱등성 덕분에 재시도가 안전하다** ([eventlooped](https://www.eventlooped.com/backend-system-design/write-offloading)).

**Snapshot을 뜬 뒤 백그라운드에서 저장한다.** 백그라운드 스레드에서 저장하기 전에 **인메모리 상태의 일관된 스냅샷을 먼저 확보**한다. 저장 도중 상태가 바뀌는 일을 피하기 위해서다. Linux/Unix MMO는 copy-on-write(vfork)로 특정 시점의 스냅샷을 적은 비용으로 만들 수 있다 ([gamedev.SE - periodically saving](https://gamedev.stackexchange.com/questions/31944/best-practices-for-periodically-saving-game-state-to-disk)). durable-workflow-snapshot 패턴은 각 스텝 후, suspend할 때, 위험한 작업 전에 전체 상태를 버전이 붙은 스키마로 직렬화해 저장소(Postgres/S3/Redis)에 넣는다. 재개할 때는 이를 읽어 rehydrate한다 ([agentpatternscatalog](https://github.com/agentpatternscatalog/patterns/blob/main/patterns/durable-workflow-snapshot.md)). 분산 실행 모델은 event log와 최신 state snapshot이라는 두 아티팩트를 함께 둔다. 워커가 크래시하면 새 워커가 둘을 맞춰 보고(reconcile), `node_id:iteration` 멱등 키로 이미 적용된 액션을 다시 실행하지 않는다 ([flattop.io](https://flattop.io/docs/concepts/distributed-execution/)).

**백업-쓰기-교체(atomicity vs durability).** 파일 세계의 기준 방식은 **temp 파일에 write → fsync → atomic rename** 이다. atomicity(크래시 후 old나 new 중 하나만 보이는 것)는 rename이 담당하고, durability(실제로 영속되는 것)는 fsync가 담당한다. 변형으로는 append-only+체크포인트(mini-WAL), double-buffered A/B 슬롯(포인터 교체) 등이 있다 ([0xKiire - Atomic File Save Patterns](https://0xkiire.com/atomic-file-save-patterns/)).

> **본 스택 매핑(대상과 어긋남에 주의).** 위의 temp+rename/backup-swap 라이브러리들은 우리가 *마이그레이션해 떠나는* 1993 디스크 세이브 방식에 속한다. MongoDB로 옮긴 뒤의 대응물은 **단일 문서 원자적 `replaceOne`/upsert** 다. Mongo는 문서 단위 원자성을 보장하므로, 캐릭터 세이브 하나를 문서 하나로 두면 별도의 파일 스왑 라이브러리가 필요 없다. 게임 서버 안에서 "백업-쓰기-교체"를 구현하는 방법은 write-behind 큐(durable queue)에 pending write를 두어 다시 재생할 수 있게 하는 것이다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/), [Ehcache](https://www.ehcache.org/documentation/2.8/apis/write-through-caching.html)).

## 3. MongoDB 트랜잭션 원자성 (경제·은행)

**기준 API.** 단일 문서 연산은 원자적이지만, 여러 문서에 걸친 원자성에는 트랜잭션이 필요하다. 트랜잭션은 여러 연산, 컬렉션, 문서에 걸칠 수 있고 replica set에서 지원된다 ([MongoDB Manual - Transactions](https://www.mongodb.com/docs/manual/core/transactions/)). Node.js 드라이버의 **Convenient API** `session.withTransaction(callback)`은 트랜잭션의 시작, 실행, 커밋을 자동으로 처리하고 일시적 에러에 대한 재시도 로직을 내장한다. 지켜야 할 점은 세 가지다. 각 연산에 같은 `session`을 넘겨야 한다. 트랜잭션 안에서 `Promise.all` 같은 병렬 실행은 undefined behavior이므로 순서대로 실행한다. 콜백 안에서 에러를 삼키지 말고 rejection을 전파해야 드라이버가 재시도할지 중단할지 판단할 수 있다 ([MongoDB Node Driver - Transactions](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/), [Convenient Transaction API](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/transaction-conv/)). 공식 예제는 주문 처리에서 재고가 부족하면 abort해서, "모든 업데이트+영수증이 적용되거나 아무것도 적용되지 않음"을 보장한다 ([Convenient Transaction API](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/transaction-conv/)).

**단일 문서 대안(트랜잭션 없이 원자성과 멱등 확보).** 은행 출금이나 이체를 `updateOne`+`find` 대신 **조건부 `findOneAndUpdate`** 로 구현할 수 있다. 그러면 잔액 검사(`balance >= amount`)와 `$inc` 차감이 하나의 원자 연산으로 수행되고, 갱신된 문서가 반환된다. 반환된 문서가 없으면 잔액 부족으로 거부한다. 이 방식은 동시 출금 race를 막고, 재시도해도 같은 결과를 돌려주므로 **멱등**하며, 잔액이 음수가 되지 않게 강제한다 ([Franck Pachot - findOneAndUpdate](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)). 두 계정 사이 이체처럼 여러 문서가 함께 성공하거나 실패해야 하면 `withTransaction`을 쓴다. 한 문서 안의 원자 갱신으로 표현할 수 있으면 `findOneAndUpdate`가 더 저렴하다.

**경제 무결성 가드.** "아이템 구매 + 골드 차감"은 반드시 하나의 작업 단위로 묶어야 한다. 둘 다 커밋되거나 둘 다 롤백되어야 한다. 그렇지 않으면 아이템을 공짜로 얻거나 골드가 사라져 경제가 깨진다 ([Tencent Cloud](https://www.tencentcloud.com/techpedia/138208)). 프로덕션 이체 백엔드들에는 공통 패턴이 있다.
- **idempotencyKey 필수**: 같은 키로 다시 요청하면 원래 결과를 돌려준다.
- **비음수 잔액 가드**: ledger 집계에서 잔액을 계산한다.
- **double-entry ledger**: DEBIT/CREDIT 쌍을 원자적으로 기록해 합이 0이 되게 한다.
- 트랜잭션 세션 안에서 여러 단계를 실행하고, 실패하면 abort한다 ([Banking-Backend-System](https://github.com/pran5hu-p/Banking-Backend-System), [Aether Economy](https://docs.aethervr.dev/docs/guides/social-economy/economy)).

대안으로 Redis Lua 스크립트가 잔액 검사와 차감을 원자적으로 처리할 수 있다 ([oneuptime - Redis currency](https://oneuptime.com/blog/post/2026-03-31-redis-in-game-currency-system/view)). 하지만 본 스택은 Redis를 쓰지 않으므로 MongoDB 경로를 택한다. 기존 커밋에 이미 `character/bank/world` repository와 gold guard가 있다. 따라서 은행 write는 이 가드에 `withTransaction`이나 조건부 `findOneAndUpdate`를 더하면 된다.

## 4. 인메모리 권위 상태 + write-behind 선례·함정

**선례: 인메모리가 source of truth.** MMO 아키텍처의 정설은 "진짜 source of truth는 인메모리 월드 상태이지 DB가 아니다"이다. DB를 SoT로 삼으면 write가 너무 많아지고 지연이 생겨 병목이 된다. data-broker 서비스가 월드 상태 전체를 메모리에 들고 스토리지에 직접 연결한다. 이 서비스는 **복구에 필요한 필수 데이터만** 영속화하고, CAS와 버전 해시로 동시성을 지킨다 ([PRDeving](https://prdeving.wordpress.com/2023/09/29/mmo-architecture-source-of-truth-dataflows-i-o-bottlenecks-and-how-to-solve-them/)). 반대쪽 설계도 있다. Postgres를 권위 있는 SoT로 두고, Redis에는 **다시 만들 수 있는 파생/hot 상태만** 담으며, authoritative 상태는 Redis에 절대 두지 않는다 ([packagemain](https://packagemain.tech/p/persistent-multiplayer-state-without)). 연구 문헌(VLDB write-back)은 다음과 같이 정리한다.
- datastore를 critical path에서 빼면 부하가 커져도 처리량이 선형으로 늘어난다.
- 하지만 buffered write가 저절로 내구성을 갖지는 않는다. 캐시 크래시를 견디려면 메모리 pin과 복제(3+)나 NVM이 필요하다.
- non-idempotent write(증분 등)는 실패할 때 따로 다뤄야 한다 ([VLDB - Write-Back](https://vldb.org/pvldb/vol12/p836-ghandeharizadeh.pdf)).

> **본 스택 매핑.** 위의 Redis hot layer 선례들은 캐시+DB의 2계층을 가정한다. 우리 아키텍처는 단일 프로세스 객체 그래프에서 Mongo로 바로 저장하므로 **프로세스 메모리 자체가 hot layer**이고 Redis 계층이 없다. 따라서 우리의 위험 모델은 "Redis 크래시로 인한 유실"이 아니라 "프로세스 크래시로 인한 유실"이다.

**함정 1: flush 전에 크래시하거나 종료하면 유실된다(가장 잘 문서화된 실사례).** Orleans 20-silo 클러스터에서는 타이머가 매분 dirty 상태를 SQL에 쓴다. 그런데 **유지보수 shutdown이 주기 flush 바로 전에 일어나면** 최근에 바뀐 grain 상태(예: List)가 사라지거나 기본값으로 돌아간다. 완화책은 `OnDeactivateAsync`에서 dirty이면 `WriteStateAsync`를 강제로 호출하는 것이다(flush-on-deactivate). 새 activation과의 race를 막으려면 분산 락도 고려한다. 스레드의 결론은 이렇다. write-behind는 graceful shutdown에서도 본질적으로 유실 위험이 있으므로, 강한 내구성이 필요하면 변경될 때마다 바로 write하는 것이 안전하다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)). → **우리 대응: 서버 shutdown 훅과 캐릭터 로그아웃에서 강제로 flush한다.**

**함정 2: 데이터 유실 창(data-loss window).** write-behind는 sub-ms 안에 ACK를 주지만, backing store에 쓰이기 전까지는 내구성이 없다. 그래서 flush interval만큼 유실 창이 생긴다. Redis AOF `appendfsync everysec`는 크래시 때 최대 1초를 잃고, 직접 만든 배치 flush도 비슷하게 유실 창이 정해진다. **돈이나 주문처럼 상위 소스에서 다시 만들 수 없는 데이터에는 write-behind를 쓰지 말아야 한다** ([hld.handbook.academy](https://hld.handbook.academy/trade-offs/cache-strategies/), [layrs.me](https://layrs.me/course/hld/07-caching/write-behind/)). 완화책은 두 가지다. 동기 WAL(ACK 전에 durable log에 append, +2–5ms)을 두어 크래시 후 재생할 수 있게 한다. 그리고 DB write를 at-least-once로 보고 **멱등 upsert**로 처리한다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)).

**함정 3: back-pressure, 즉 writer가 뒤처지는 문제.** Akka.NET에서 블로킹 `Persist`는 영속화가 끝날 때까지 액터를 막아 back-pressure와 stash를 일으킨다. 부하나 CPU 사용량이 높으면 **메시지 드롭, DeadLetter, journal 타임아웃으로 인한 액터 종료**로 이어진다. 완화책은 `PersistAll`로 배칭하고, 공유 journal을 써서 액터마다 DB 커넥션을 두지 않으며, 필요하면 일관성이 약한 `PersistAsync`를 쓰는 것이다 ([Akka.NET back-pressure](https://stackoverflow.com/questions/65918832/akka-net-with-persistence-dropping-messages-when-cpu-in-under-high-pressure)). Ehcache write-behind 큐도 메모리에 있어서 JVM이 종료되면 큐가 사라질 수 있다. 원격 durable 큐를 쓰면 내구성과 HA를 얻는다 ([Ehcache](https://www.ehcache.org/documentation/2.8/apis/write-through-caching.html)). → **우리 대응: bounded 큐와 coalescing으로 writer 부하에 상한을 두고, 종료할 때 큐를 반드시 비운다.**

**함정 4: fire-and-forget이나 비원자적 영속화는 상태 불일치를 만든다.** Orleans 표준 provider(Azure/Redis)에서 `Task.Factory.StartNew`로 persist를 따로 띄우면 etag/state 불일치(`InconsistentStateException`)가 난다. 중요한 상태 write는 fire-and-forget으로 두지 말고 **await**해서 순서와 일관성을 지켜야 한다 ([Orleans #9276](https://github.com/dotnet/orleans/issues/9276)).

## Key Takeaways

- **하이브리드 세이브 정책 엔진을 채택한다**: 1Hz 틱에서 dirty 엔티티만 주기적으로 flush하고(권장 출발값 60–300초, *판단*), 중요 이벤트(레벨업, 거래, 로그아웃)는 바로 write한다. 이는 LuminariMUD의 `PULSE_AUTOSAVE`(매분)와 이벤트 저장 선례와 일치한다 ([LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md), [gamedev.SE](https://gamedev.stackexchange.com/questions/19338/how-often-to-save-players-state-in-persistent-online-games)).
- **shutdown/deactivate 때의 강제 flush를 핵심 요건으로 둔다**: Orleans #9655가 보여 준 가장 큰 함정, 즉 주기 flush 직전 종료로 인한 유실을 막는다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)).
- **entity별 dirty 추적과 write coalescing**(last-write-wins dedup)으로 write amplification과 writer back-pressure를 함께 줄인다 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/), [marathon RFC 0002](https://github.com/r3t-studios/marathon/blob/HEAD/docs/rfcs/0002-persistence-strategy.md)).
- **틱과 I/O를 분리한다**: bounded 큐와 async writer를 써서 Mongo write가 틱을 막지 않게 하고, 종료할 때 큐를 반드시 비운다 ([mygamehost](https://mygamehost.net/en/wiki/synchronous-vs-asynchronous-how-databases-dictate-game-tps-stability), [eventlooped](https://www.eventlooped.com/backend-system-design/write-offloading)).
- **파일 backup-swap 대신 Mongo 문서 원자성을 쓴다**: 캐릭터 세이브를 단일 문서로 두고 원자적 `replaceOne`/upsert로 저장한다. 파일 temp+rename 라이브러리는 필요 없다(마이그레이션 대상이다) ([MongoDB Manual](https://www.mongodb.com/docs/manual/core/transactions/)).
- **은행/경제는 강한 내구성 경로로 따로 둔다**: write-behind를 쓰면 안 되는 대상이다. 여러 계정 사이 이체는 `withTransaction`(재시도 내장)으로, 단일 계정 차감은 조건부 `findOneAndUpdate`+`$inc`로 처리해 원자성, 비음수, 멱등을 지킨다. 여기에 **idempotencyKey**와 기존 gold guard를 함께 쓴다 ([MongoDB Node Driver](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/), [Franck Pachot](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)).
- **멱등 upsert를 기본 write 형태로 둔다**: async writer는 at-least-once이므로, 재시도가 중복을 만들지 않도록 upsert 기반으로 설계한다 ([techinterview](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)).
- **유실 창을 명시적인 정책으로 문서화한다**: 주기 flush를 택하면 "최대 N초 유실 가능"을 받아들인 트레이드오프로 스펙에 적는다(돈은 제외) ([hld.handbook.academy](https://hld.handbook.academy/trade-offs/cache-strategies/)).

## Methodology
Searched 14 queries (Exa 10 + Firecrawl 4). 두 어댑터 모두 정상이었다(키 200 OK, 실패 없음). 어댑터는 adapter-exa(primary/deep-read, `/search` type=auto, contents+summary)와 adapter-firecrawl(secondary, `/v1/search`)을 썼다. Sub-questions는 다음 4개다. (1) dirty-flag 주기 flush + 이벤트 즉시 write, (2) snapshot→queue→async worker + 백업-쓰기-교체 내구성, (3) MongoDB 트랜잭션 원자성(경제·은행), (4) 인메모리 권위 상태 write-behind 선례와 함정. sub-question마다 키워드 변형을 2–3개 썼다. 분석한 원천 40+개(Exa 30+, Firecrawl 20+) 가운데 품질 기준에 맞는 30개를 인용했다. 기준은 공식 문서, 엔지니어링 블로그, MMO/게임 서버 write-up을 우선하고 포럼과 소셜은 빼는 것이다. reddit/facebook/youtube/scribd 등은 출처 수가 부풀려지지 않도록 제외했다.
