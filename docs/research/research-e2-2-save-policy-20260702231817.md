# E2-2 세이브 정책 엔진: Research Report

> 주: 아래 인용 스니펫 상당수는 Exa가 생성한 페이지 LLM 요약이며 원문 raw 텍스트가 아니다. 6개 이상 소스에서 교차 확인된 주장(write-behind 내구성 트레이드오프 등)은 신뢰 가능하나, 단일 요약에만 근거한 하중 주장은 세우지 않았다.

## Executive Summary

권위 상태를 프로세스 메모리에 두고 MongoDB에 영속화하는 서버의 정본 패턴은 **dirty-flag 기반 write-behind(write-back)** 이다. 라이브 틱은 인메모리 상태만 변경하고, 변경분을 dirty로 표시한 뒤 (a) 주기 타이머 flush와 (b) 치명 이벤트(레벨업·거래·로그아웃) 즉시 write, (c) **종료 시 강제 flush**로 내구성을 확보한다 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/), [layrs.me](https://layrs.me/course/hld/07-caching/write-behind/), [LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md)). MMO 아키텍처 통설은 "인메모리 월드 상태가 진짜 source of truth이고 DB는 복구용 영속화"이며, 이는 본 프로젝트의 단일프로세스 객체그래프+DB네이티브 세이브 결정과 정확히 일치한다 ([PRDeving](https://prdeving.wordpress.com/2023/09/29/mmo-architecture-source-of-truth-dataflows-i-o-bottlenecks-and-how-to-solve-them/)). 경제·은행 무결성은 MongoDB 다중문서 트랜잭션(`withTransaction`) 또는 단일문서 조건부 `findOneAndUpdate`+`$inc`로 원자성·비음수·멱등을 동시 달성한다 ([MongoDB Docs](https://www.mongodb.com/docs/manual/core/transactions/), [Franck Pachot](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)). 가장 잘 문서화된 함정은 **write-behind에서 flush 전 크래시/종료 시 최근 변경 유실**이며(Orleans 실사례), 완화책은 deactivate/shutdown 훅에서의 강제 flush와 멱등 upsert다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)).

## 1. Dirty-flag 주기 flush + 이벤트 즉시 write

**핵심 워크플로우.** 엔티티별 인메모리 버퍼가 변경 시 필드를 dirty로 마킹하고, 주기 tick(alarm)이 dirty 필드만 정본 저장소에 write한 뒤 dirty 플래그를 클리어한다. 필드 단위 dirty 추적은 write amplification을 줄인다 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/)). game state를 통째 blob으로 쓰지 말고 (1) 정말 중요한 부분만, (2) 마지막 저장 이후 변경된 것만, (3) 개별적으로 저장하라는 것이 게임 세이브의 정설이다 ([gamedev.SE - periodically saving](https://gamedev.stackexchange.com/questions/31944/best-practices-for-periodically-saving-game-state-to-disk)).

**MUD 직접 선례.** LuminariMUD는 pulse 기반 메인루프에서 `PULSE_AUTOSAVE`로 **매 분마다** `Crash_save_all()`을 호출해 플레이어 데이터를 주기 영속화하고, 종료 시퀀스에서도 저장한다. 레벨업 같은 치명 이벤트는 autosave 경로나 직접 save 호출로 즉시 반영하도록 확장 가능하다고 명시한다 ([LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md)). 또 다른 MUD 논의는 핵심 캐릭터 데이터(아이템·스킬·진행)를 주기 저장하고, **레벨업·영역 이동·보스 처치·상점 이탈·로그아웃/연결끊김에 즉시 저장**하되, 매 틱 모든 NPC 위치를 저장하지는 말라고 권한다 ([gamedev.SE - how often to save](https://gamedev.stackexchange.com/questions/19338/how-often-to-save-players-state-in-persistent-online-games)). 단일플레이어 AI-MUD는 몹 HP가 히트 사이에 stale 재로딩으로 회복되는 버그를 막기 위해 "매 공격 틱마다 zone 상태 저장" 규칙을 둔다 — **저장 타이밍 누락이 실제 게임 버그로 이어지는** 사례다 ([SINGLE-PLAYER-AI-MUD](https://github.com/undergroundrap/SINGLE-PLAYER-AI-MUD)).

**Flush 간격·write coalescing 트레이드오프.** 시간 기반 배칭(예: 5초/1분)은 DB 부하가 예측 가능하나 최대 한 interval만큼 데이터가 캐시에 머문다 ([layrs.me](https://layrs.me/course/hld/07-caching/write-behind/)). count 기반 flush(dirty 수 임계 초과 시)는 메모리 압력을 제한하며 interval 기반과 병행하는 것이 보편적이다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)). **write coalescing**: 같은 엔티티+컴포넌트에 대한 다중 pending write를 최신값 하나로 dedup — 60fps 드래그가 만든 ~300 transform 업데이트가 단일 write로 합쳐진다(last-write-wins) ([marathon RFC 0002](https://github.com/r3t-studios/marathon/blob/HEAD/docs/rfcs/0002-persistence-strategy.md), [techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)). 한 실제 SQL.js 프로젝트는 고정 60초 interval autosave를 **dirty-flag + 60초 debounce**로 교체해 idle 시 write를 0으로 만들면서 동일한 최대 staleness(60초)를 유지했다 ([SeekerClaw PR#347](https://github.com/sepivip/SeekerClaw/pull/347)). Roblox용 오픈소스 Lyra는 lock-backed 세션마다 non-yielding 백그라운드 autosave 루프를 돌리며 shutdown 시 최종 저장을 수행한다 ([Lyra Session](https://github.com/paradoxum-games/lyra/blob/e40d12a8/src/Session.luau)).

**간격 권장(판단, 소스는 단일값이 아닌 범위 제시).** 소스들은 5초~수분까지 폭넓게 제시하며 단일 정답이 없다. 본 프로젝트(1Hz 틱, 소규모 동접)에는 **60–300초 주기 flush + 치명 이벤트 즉시 write** 조합이 합리적 출발점이다. 이는 원본 무한/Mordor의 분 단위 autosave 감각(LuminariMUD 매분)과도 부합한다.

## 2. Snapshot→queue→async worker 파이프 + 백업-쓰기-교체 내구성

**틱 루프와 I/O의 분리.** 스토리지 I/O 지연이 메인 게임 루프(물리·플레이어 추적·TPS)를 블록하지 않도록, 메인 스레드는 DB 커맨드를 dispatch만 하고 결과를 기다리지 않으며 백그라운드 워커가 모든 DB I/O를 처리한다. 완료 시 콜백/이벤트로 메인 루프에 반영한다 ([mygamehost](https://mygamehost.net/en/wiki/synchronous-vs-asynchronous-how-databases-dictate-game-tps-stability)). 이는 고전 **Event Queue 패턴** — 생산자(게임 로직)가 write 이벤트를 enqueue하고 별도 워커가 큐를 drain해 I/O를 수행, 프레임을 블록하지 않는다 ([Game Programming Patterns - Event Queue](https://gameprogrammingpatterns.com/event-queue.html), [Socratopia](https://www.socratopia.app/library/game-code-anatomy-en/chapter-15)). **Write Offloading**: 게임서버가 버퍼/큐에 빠르게 ACK(1–5ms)하고 워커가 지속 가능한 속도로 배치 write하며, 세션 단위 파티셔닝으로 순서를 보존하고 **멱등성으로 재시도를 안전하게** 만든다 ([eventlooped](https://www.eventlooped.com/backend-system-design/write-offloading)).

**Snapshot 후 백그라운드 저장.** 백그라운드 스레드에서 저장하기 전에 **인메모리 상태의 일관된 스냅샷을 먼저 확보**해 mid-save mutation을 피한다. Linux/Unix MMO는 copy-on-write(vfork)로 시점 스냅샷을 저효율로 만들 수 있다 ([gamedev.SE - periodically saving](https://gamedev.stackexchange.com/questions/31944/best-practices-for-periodically-saving-game-state-to-disk)). durable-workflow-snapshot 패턴은 각 스텝 후·suspend 시·위험 작업 전에 전체 상태를 버전드 스키마로 직렬화해 저장소(Postgres/S3/Redis)에 넣고, 재개 시 로드·rehydrate한다 ([agentpatternscatalog](https://github.com/agentpatternscatalog/patterns/blob/main/patterns/durable-workflow-snapshot.md)). 분산 실행 모델은 **event log + 최신 state snapshot** 두 아티팩트를 병행해, 워커 크래시 시 새 워커가 둘을 reconcile하고 `node_id:iteration` 멱등 키로 이미 적용된 액션 재실행을 방지한다 ([flattop.io](https://flattop.io/docs/concepts/distributed-execution/)).

**백업-쓰기-교체(atomicity vs durability).** 파일 세계의 정본은 **temp 파일 write → fsync → atomic rename**이며, atomicity(크래시 후 old 또는 new만 보임)는 rename이, durability(실제 영속)는 fsync가 담당한다. 변형으로 append-only+체크포인트(mini-WAL), double-buffered A/B 슬롯(포인터 교체) 등이 있다 ([0xKiire - Atomic File Save Patterns](https://0xkiire.com/atomic-file-save-patterns/)).

> **본 스택 매핑(off-target 주의).** 위 temp+rename/backup-swap 라이브러리들은 우리가 *마이그레이션해 나오는* 1993 디스크 세이브 세계의 것이다. MongoDB로 옮긴 뒤 등가물은 **단일 문서 원자적 `replaceOne`/upsert** 다 — Mongo는 문서 단위 원자성을 보장하므로, 한 캐릭터 세이브를 한 문서로 두면 별도 파일-스왑 라이브러리가 불필요하다. "백업-쓰기-교체"의 게임서버 내 실현은 write-behind 큐(durable queue)로 pending write를 재생 가능하게 두는 것이다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/), [Ehcache](https://www.ehcache.org/documentation/2.8/apis/write-through-caching.html)).

## 3. MongoDB 트랜잭션 원자성 (경제·은행)

**정본 API.** 단일 문서 연산은 원자적이지만, 다중 문서 원자성은 트랜잭션이 필요하다. 트랜잭션은 여러 연산·컬렉션·문서에 걸칠 수 있고 replica set에서 지원된다 ([MongoDB Manual - Transactions](https://www.mongodb.com/docs/manual/core/transactions/)). Node.js 드라이버의 **Convenient API** `session.withTransaction(callback)`는 트랜잭션 시작·실행·커밋을 자동화하고 **일시적 에러에 대한 재시도 로직을 내장**한다. 각 연산에 동일 `session`을 전달해야 하며, 트랜잭션 내부에서 `Promise.all` 등 병렬 실행은 undefined behavior이므로 순차 실행하고, 콜백 내에서 에러를 swallow하지 말고 rejection을 전파해야 드라이버가 재시도/중단을 판단한다 ([MongoDB Node Driver - Transactions](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/), [Convenient Transaction API](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/transaction-conv/)). 공식 예제는 주문 처리에서 재고 부족 시 abort하여 "모든 업데이트+영수증이 적용되거나 아무것도 적용되지 않음"을 보장한다 ([Convenient Transaction API](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/transaction-conv/)).

**단일문서 대안(트랜잭션 없이 원자성·멱등).** 은행 출금/이체를 `updateOne`+`find` 대신 **조건부 `findOneAndUpdate`** 로 구현하면 잔액 검사(`balance >= amount`)와 `$inc` 차감을 단일 원자 연산으로 수행하고 갱신 후 문서를 반환한다. 반환 문서가 없으면 잔액 부족으로 거부 — 이는 동시 출금 race를 막고, 재시도 시 동일 결과를 돌려주어 **멱등**하며, **비음수 잔액을 강제**한다 ([Franck Pachot - findOneAndUpdate](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)). 두 계정에 걸친 이체처럼 다중 문서가 함께 성공/실패해야 하면 `withTransaction`을 쓰고, 한 문서 내 원자 갱신으로 표현 가능하면 `findOneAndUpdate`가 더 저렴하다.

**경제 무결성 가드.** "아이템 구매 + 골드 차감"은 반드시 단일 작업 단위로 묶어 둘 다 커밋 또는 둘 다 롤백해야 하며, 그렇지 않으면 무료 아이템 획득이나 골드 증발이 발생해 경제가 깨진다 ([Tencent Cloud](https://www.tencentcloud.com/techpedia/138208)). 프로덕션 이체 백엔드들의 공통 패턴: **idempotencyKey 필수**(동일 키 재요청은 원래 결과 반환), **비음수 잔액 가드**(ledger 집계로 파생), **double-entry ledger**(DEBIT/CREDIT 쌍을 원자적으로 기록해 합이 0), 트랜잭션 세션 내 다단계 실행 후 실패 시 abort ([Banking-Backend-System](https://github.com/pran5hu-p/Banking-Backend-System), [Aether Economy](https://docs.aethervr.dev/docs/guides/social-economy/economy)). 대안으로 Redis Lua 스크립트가 잔액 검사+차감을 원자적으로 처리하지만 ([oneuptime - Redis currency](https://oneuptime.com/blog/post/2026-03-31-redis-in-game-currency-system/view)), 본 스택은 Redis 미도입이므로 MongoDB 경로를 택한다. 기존 커밋에 이미 `character/bank/world` repository와 gold guard가 있으므로, 은행 write는 이 가드 위에 `withTransaction` 또는 조건부 `findOneAndUpdate`를 얹으면 된다.

## 4. 인메모리 권위 상태 + write-behind 선례·함정

**선례: 인메모리가 source of truth.** MMO 아키텍처의 정설은 "진짜 source of truth는 인메모리 월드 상태이지 DB가 아니다"이다. DB를 SoT로 삼으면 과도한 write와 지연으로 병목이 생긴다. data-broker 서비스가 전체 월드 상태를 메모리에 보유하고 스토리지에 직결하며, **복구에 필요한 필수 데이터만** 영속화하고 CAS·버전 해시로 동시성을 지킨다 ([PRDeving](https://prdeving.wordpress.com/2023/09/29/mmo-architecture-source-of-truth-dataflows-i-o-bottlenecks-and-how-to-solve-them/)). 반대 스펙트럼으로, Postgres를 권위 SoT로 두고 Redis는 **재구성 가능한 파생/hot 상태만** 담아 authoritative 상태를 Redis에 절대 두지 않는 설계도 있다 ([packagemain](https://packagemain.tech/p/persistent-multiplayer-state-without)). 연구 문헌(VLDB write-back)은 datastore를 critical path에서 제거해 부하 하에서도 처리량이 선형 확장되지만, buffered write는 자동으로 내구적이지 않으며 **메모리 pin + 복제(3+) 또는 NVM**으로 캐시 크래시를 견뎌야 하고, non-idempotent write(증분 등)는 실패 시 특별 취급이 필요하다고 정리한다 ([VLDB - Write-Back](https://vldb.org/pvldb/vol12/p836-ghandeharizadeh.pdf)).

> **본 스택 매핑.** 위 Redis-hot-layer 선례들은 2계층(캐시+DB)을 가정한다. 우리 아키텍처는 단일프로세스 객체그래프 → Mongo이므로 **프로세스 메모리 자체가 hot layer**이고 Redis 계층을 생략한다. 따라서 "Redis 크래시로 유실" 대신 "프로세스 크래시로 유실"이 우리의 위험 모델이다.

**함정 1: flush 전 크래시/종료 시 유실(가장 잘 문서화된 실사례).** Orleans 20-silo 클러스터에서 타이머가 매분 dirty 상태를 SQL에 write하는데, **유지보수 shutdown이 주기 flush 직전에 일어나면** 최근 변경된 grain 상태(예: List)가 유실되거나 기본값으로 되돌아간다. 완화책은 `OnDeactivateAsync`에서 dirty면 강제 `WriteStateAsync`(flush-on-deactivate)하는 것이며, 새 activation과의 race를 막기 위해 분산 락을 고려한다. 스레드 결론: write-behind는 graceful shutdown에서도 본질적으로 유실 위험이 있어, 강한 내구성이 필요하면 매 변경 즉시 write가 안전하다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)). → **우리 대응: 서버 shutdown 훅과 캐릭터 로그아웃에서 강제 flush.**

**함정 2: 데이터 유실 창(data-loss window).** write-behind는 sub-ms ACK를 주지만 backing store에 쓰이기 전까지 내구적이지 않아, flush interval만큼의 유실 창이 존재한다. Redis AOF `appendfsync everysec`는 크래시 시 최대 1초 유실이며, 커스텀 배치 flush도 유사하게 창을 정의한다. **돈·주문처럼 상위 소스에서 재구성 불가능한 데이터에는 write-behind를 쓰지 말라** ([hld.handbook.academy](https://hld.handbook.academy/trade-offs/cache-strategies/), [layrs.me](https://layrs.me/course/hld/07-caching/write-behind/)). 완화: **동기 WAL**(ACK 전 durable log append, +2–5ms)로 크래시 후 재생 가능하게 하고, DB write는 at-least-once로 취급해 **멱등 upsert**로 처리한다 ([techinterview - write-behind LLD](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)).

**함정 3: back-pressure — writer가 뒤처짐.** Akka.NET에서 블로킹 `Persist`는 영속화 완료까지 액터를 블록해 back-pressure와 stash를 유발하고, 고부하/높은 CPU에서 **메시지 드롭·DeadLetter·journal 타임아웃으로 인한 액터 종료**로 이어진다. 완화는 `PersistAll` 배칭, 공유 journal로 per-actor DB 커넥션 회피, 필요 시 약한 일관성의 `PersistAsync` ([Akka.NET back-pressure](https://stackoverflow.com/questions/65918832/akka-net-with-persistence-dropping-messages-when-cpu-in-under-high-pressure)). Ehcache write-behind 큐도 인메모리라 JVM 종료 시 큐 유실이 가능하며, 원격 durable 큐로 내구성/HA를 얻는다 ([Ehcache](https://www.ehcache.org/documentation/2.8/apis/write-through-caching.html)). → **우리 대응: bounded 큐 + coalescing으로 writer 부하를 상한, 종료 시 큐 drain 보장.**

**함정 4: fire-and-forget/비원자 영속화로 상태 불일치.** Orleans 표준 provider(Azure/Redis)에서 `Task.Factory.StartNew`로 persist를 spawn하면 etag/state mismatch(`InconsistentStateException`)가 난다. 치명 상태 write는 fire-and-forget 대신 **await**해 순서·일관성을 지켜야 한다 ([Orleans #9276](https://github.com/dotnet/orleans/issues/9276)).

## Key Takeaways

- **하이브리드 세이브 정책 엔진 채택**: 1Hz 틱에서 dirty 엔티티만 주기 flush(권장 출발값 60–300초, *판단*) + 치명 이벤트(레벨업·거래·로그아웃) 즉시 write. 이는 LuminariMUD의 `PULSE_AUTOSAVE`(매분) + 이벤트 저장 선례와 정합 ([LuminariMUD](https://github.com/LuminariMUD/Luminari-Source/blob/fcd29e77394ad03359a2ae80ac29fc549aa54338/docs/systems/CORE_SERVER_ARCHITECTURE.md), [gamedev.SE](https://gamedev.stackexchange.com/questions/19338/how-often-to-save-players-state-in-persistent-online-games)).
- **shutdown/deactivate 강제 flush를 1급 요건으로**: Orleans #9655가 증명한 유일 최대 함정(주기 flush 직전 종료 유실)을 닫는다 ([Orleans #9655](https://github.com/dotnet/orleans/issues/9655)).
- **entity별 dirty 추적 + write coalescing**(last-write-wins dedup)으로 write amplification과 writer back-pressure를 동시에 억제 ([happyin.space](https://happyin.space/architecture/write-buffering-patterns/), [marathon RFC 0002](https://github.com/r3t-studios/marathon/blob/HEAD/docs/rfcs/0002-persistence-strategy.md)).
- **틱과 I/O 분리**: bounded 큐 + async writer로 Mongo write가 틱을 블록하지 않게 하고, 종료 시 큐 drain을 보장 ([mygamehost](https://mygamehost.net/en/wiki/synchronous-vs-asynchronous-how-databases-dictate-game-tps-stability), [eventlooped](https://www.eventlooped.com/backend-system-design/write-offloading)).
- **파일 backup-swap 대신 Mongo 문서 원자성 활용**: 캐릭터 세이브를 단일 문서로 두고 원자적 `replaceOne`/upsert; 파일 temp+rename 라이브러리는 불필요(마이그레이션 대상) ([MongoDB Manual](https://www.mongodb.com/docs/manual/core/transactions/)).
- **은행/경제는 강한 내구성 경로로 분리**: write-behind 금지 대상. 다중 계정 이체는 `withTransaction`(재시도 내장), 단일 계정 차감은 조건부 `findOneAndUpdate`+`$inc`로 원자·비음수·멱등. **idempotencyKey**와 기존 gold guard를 결합 ([MongoDB Node Driver](https://www.mongodb.com/docs/drivers/node/current/crud/transactions/), [Franck Pachot](https://dev.to/franckpachot/acid-and-idempotent-update-returning-in-mongodb-with-findoneandupdate-955)).
- **멱등 upsert를 기본 write 형태로**: async writer는 at-least-once이므로 재시도가 중복을 만들지 않게 upsert 기반으로 설계 ([techinterview](https://www.techinterview.org/post/3233469260/lld-write-behind-cache/)).
- **유실 창을 명시적 정책으로 문서화**: 주기 flush 선택 시 "최대 N초 유실 가능"을 수용된 트레이드오프로 스펙에 기록(돈 제외) ([hld.handbook.academy](https://hld.handbook.academy/trade-offs/cache-strategies/)).
