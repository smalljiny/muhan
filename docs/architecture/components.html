무한 컴포넌트 다이어그램 — 무엇이 실제로 이어져 있나

C4 방식 3레벨입니다. 이 프로젝트는 배포 단위가 서버 프로세스 하나라 Context와 Container 레벨이 붕괴하므로, L1은 패키지 목록이 아니라 시스템 컨텍스트(외부 경계 + 빌드타임 입력)로 잡았습니다.

간선은 포함 관계가 아니라 배선 상태를 인코딩합니다 — 초록 실선은 프로덕션에서 실제로 흐르는 경로, 붉은 점선은 seam은 있으나 noop이거나 호출처가 없는 경로입니다. 포함 관계는 LSP 도구가 라이브로 더 정확히 답하고, 이 프로젝트를 두 번 놀라게 한 것은 "배선만 하면 된다"는 전제였습니다. 간선에 커서를 올리면 계약·주입 지점·이슈 번호가 뜹니다.

L1 — 시스템 컨텍스트

context · 외부 경계 + 빌드타임 입력

왼쪽 3개는 빌드타임 파이프라인입니다 — 1993년 32비트 구조체 덤프를 port/가 JSON으로 풀고, 서버는 그 JSON만 읽습니다. legacy/muhan/src는 실행 대상이 아니라 동작 명세(oracle)이고, 런타임 의존이 아니라 사람과 골든 fixture가 참조하는 경로라 점선 테두리로 뒀습니다.

실 배선 계약·참조 의존 이 저장소가 만드는 것 외부·읽기 전용 간선에 커서를 올리면 계약

L2 — 서버 내부 구획

container · 배선 상태 인코딩

이 다이어그램의 핵심은 붉은 점선 2개입니다 — 규칙 엔진으로 들어가는 진입 경로가 둘(플레이어 명령 / 몬스터 tick)인데 양쪽이 다 끊겼습니다. 규칙 레이어는 완성돼 오라클 대조까지 끝났고, 유닛 테스트는 통과하지만 프로덕션에서는 죽어 있습니다. 살아 있는 유일한 규칙 경로는 progress:train 하나입니다. 조립은 전부 index.ts(186줄) → liveWorldWiring(185줄) → plugin.ts(692줄) 단일 체인을 지납니다.

실 배선 (프로덕션에서 흐름) 미배선 (noop 또는 호출처 0건) 타입·계약 의존 간선에 커서를 올리면 seam·이슈

seam 카탈로그

table · 레벨 아님 · HEAD 재검증

이 프로젝트는 DIP seam 위에 서 있습니다. 패턴은 일관되게 명시 주입 ?? 묶음 파생 ?? 기본 어댑터이고, 기본 어댑터가 noop이라 주입을 빼먹어도 조용히 동작합니다 — 그게 이 표가 필요한 이유입니다. 아래 상태는 전부 develop fd40682에서 확인했습니다.

L3 작성 계획

6 영역 · 디렉터리 15개 전부가 아님

배선이 자명하지 않은 영역만 작성합니다. 15개 디렉터리마다 L3를 만들면 15장이 되고 ~200개 소스 파일과 동기화해야 하는 부채가 됩니다. L3 노드는 모듈(파일)까지이고, 배선 상태 오버레이는 이 문서와 같은 방식으로 HEAD 기준 재검증 후 붙입니다.

전송·세션ws · 33 모듈

FSM + 라우터 + 포트 4개 + 조립. 최대 복잡도이고 plugin.ts 692줄이 우선순위 분기(explicit > bundle > noop)를 전부 담고 있습니다.

protocol(와이어) · schema(문서) · oracle(골든 fixture) · stats. 프론트/백엔드 병행의 유일한 접점이라 경계가 문서화될 값이 큽니다.

▸ E11·E12 프로토콜 확장 전
L3를 만들지 않는 영역 — client(8 모듈) · port(3) · auth(10) · items/economy/bank(12)는 L2 리프 상자로 둡니다. 규모가 작아 L2 노드 하나 + seam 표 한 줄로 충분히 표현되고, LSP 도구가 라이브로 더 정확하게 답합니다. client는 E11·E12·E13이 착지해 컴포넌트가 늘어나면 그때 L3를 추가하는 것이 맞습니다.
